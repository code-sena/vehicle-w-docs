# Data Dictionary

`models.md` documents every column. This file is narrower on purpose: it covers only the
fields that are genuinely easy to get wrong — status codes someone will hardcode instead of
looking up, flag combinations that only make sense together, and fields whose name doesn't
fully say what they mean.

| Field | Schema | Table | Type | Detailed description | Possible values |
|-------|---------|-------|------|----------------------|------------------|
| `booking_status_id` | booking | booking | SMALLINT | Current state of a booking. ID `5` is hard-coded inside `ck_booking_cancel` and `tr_booking_bay_overlap` — never re-seed this table with a different row order. | 1 `SCHEDULED`, 2 `CONFIRMED`, 3 `IN_PROGRESS`, 4 `COMPLETED`, 5 `CANCELLED`, 6 `NO_SHOW` — 1–3 occupy the bay |
| `payment_status_id` | payment | payment | SMALLINT | Current state of a payment attempt. ID `3` is hard-coded inside `ux_payment_one_approved_per_booking`. | 1 `PENDING`, 2 `IN_REVIEW`, 3 `APPROVED`, 4 `REJECTED`, 5 `REFUNDED` |
| `execution_status_id` | execution | service_execution | SMALLINT | State of one line item's execution — independent of the parent booking's status. | 1 `PENDING`, 2 `IN_PROGRESS`, 3 `PAUSED`, 4 `COMPLETED`, 5 `WITH_ISSUE` (English codes, seed 105; the code only uses `PENDING`, `IN_PROGRESS` and `COMPLETED` today) |
| `is_public` + `min_completed_booking` | promotion | promotion | BIT + INT | Together they decide who a promotion reaches. `is_public = 1` with `min_completed_booking = 0` means every customer qualifies. `is_public = 1` with `min_completed_booking = 5` means only customers with 5+ finished bookings qualify. `is_public = 0` ignores this column entirely — eligibility comes only from `promotion_customer`. **As of 2026-10-23 the code reads neither column nor `promotion_customer`:** every active promotion in its dates is offered to every customer, gated only by `required_points`. | See description |
| `points_redeemed` + `points_discount_amount` | booking | booking | INT + DECIMAL(12,2) | Must both be zero or both be greater than zero (`ck_booking_points`). `points_redeemed` is how many loyalty points were spent; `points_discount_amount` is what those points were worth in pesos, and is the number that actually reduces the booking's charge. | Both 0, or both > 0 |
| `sign` | payment | loyalty_movement_type | SMALLINT | Whether this movement type adds or removes points from the balance. Multiply `loyalty_transaction.points` by this to get the actual balance impact. | `1` (adds), `-1` (subtracts) |
| `is_customer_fault` | booking | cancellation_reason | BIT | Marks whether a cancellation reason is attributable to the customer — used for reporting and for deciding whether a no-show penalty applies. Not the same as `is_final` on status tables. | `0`, `1` |
| `requires_account` + `requires_receipt` | payment | payment_method_type | BIT + BIT | `requires_account` is true for every seeded method (cash included — cash still has a `payment_account` row, just without a QR). `requires_receipt` is `0` only for cash; every QR-based method needs an uploaded `payment_receipt`. | `0` / `1` each |
| `reported_amount` vs `amount` | payment | payment_receipt / payment | DECIMAL(12,2) | `payment.amount` is what the system expects to be paid. `payment_receipt.reported_amount` is what the uploaded receipt claims was paid. The two are compared during manual review — a mismatch is the signal an admin acts on, not something the database blocks automatically. | Any positive value |
| `transaction_reference` | payment | payment_receipt | NVARCHAR(100) | Reference number printed on the receipt. Indexed so the use-case check (`BookingPaymentGuard`) can quickly reject a reference already used on another booking (409 `TRANSACTION_REFERENCE_REUSED`); not unique in the table, because the same booking may report it again after a rejection — the antifraud control that stands in for a real payment gateway. Since payment 023 the indexed view `v_live_transaction_reference` makes it unique among live payments (states 1–3), also under two simultaneous requests. | Free text, nullable |
| `singleton` | booking | establishment | BIT | Always `1`. Exists only so `uq_establishment_singleton` + `ck_establishment_singleton` can guarantee the table never holds more than one row. | `1` (only) |
| `size_factor` | customer | vehicle_type | DECIMAL(4,2) | Reference multiplier shown in the admin UI when creating a new tariff — never used to compute an actual charge. The real price always comes from `catalog.service_price`. | > 0 (`ck_vehicle_type_size_factor`); seeded 0.80–1.35 |
| `applied_amount` | promotion | booking_promotion | DECIMAL(12,2) | The discount a promotion actually granted, frozen at the moment it was applied — not recalculated if the promotion's terms change later. A booking has at most one row (`ux_booking_promotion_one_per_booking`, payment 021); removing the coupon deletes the row. A percentage coupon also stores `discount_percent` and `max_discount_amount` (022) and its discount is recomputed from the current total; a fixed one discounts `applied_amount`. | > 0 |
| `reference_entity` + `reference_id` | notification | notification | NVARCHAR(40) + BIGINT | Together they point at what a notification is about, e.g. `('booking', 145)`, so tapping the notification can deep-link to the right screen. Not a foreign key — `reference_entity` can name a table in any schema. | e.g. `booking`, `payment` |
| `is_read` + `read_at` | notification | notification | BIT + DATETIME2(3) | Must be set together (`ck_notification_read`): both null/`0`, or both populated. | — |
| `loyalty_points` | customer | customer | INT | Display copy of the balance. The source of truth is the latest `balance_after` in `payment.loyalty_transaction` (another service since ADR-009). Never use it to validate a redemption. As implemented (ADR-015) nothing updates it; the balance is read live from the ledger. | ≥ 0 |
| `quality_rating` + `quality_comment` + `rated_at` | execution | service_execution | SMALLINT + NVARCHAR(500) + DATETIME2(3) | The optional rating of one service line. All three NULL = not rated, which is valid. A rating needs its date (`ck_sexec_rated`); a comment needs a rating (`ck_sexec_comment`). Average with `AVG(quality_rating * 1.0)`: `AVG` ignores NULLs, and the `* 1.0` keeps SQL Server from truncating the average of an integer column (4.6 would become 4). Never `COALESCE(..., 0)`. | Rating 1–5, or all NULL |
| `loyalty_points` | catalog / booking | service / booking_service | INT | Two different numbers with the same name. `catalog.service.loyalty_points` is what the service earns **today** (the admin edits it). `booking.booking_service.loyalty_points` (043) is what it was worth **when that line was booked**, and is what payment-service credits when the booking is paid (A-09). | ≥ 0; the line copy is NULL only before the 043 backfill |
| `assignment_notes` | execution | service_execution | NVARCHAR(300) | Notes of the admin for the operator, written when assigning (B-01, 042). Optional; reassigning without notes clears them. | Free text, nullable |
| `sequence_no` | payment | loyalty_transaction | INT | Position of the movement in its client's ledger (1, 2, 3…), unique with `customer_id` (020). It is what makes two concurrent movements on the same balance fail instead of leaving a wrong `balance_after`. | 1, 2, 3… per client |
| `deleted_at` | most domain tables | — | DATETIME2(3) | `NULL` = active row; a non-null value means soft-deleted (hidden from normal queries, not removed). A few rows are deleted physically by design: `security.login_lockout`, `person_address`, `role_permission` (list replaced), `execution.operator_skill` (list replaced), `promotion.booking_promotion` (coupon removed) and a soft-deleted `business_hour_exception` that blocks reusing its date. | `NULL` or a UTC timestamp |
| `row_version` | domain tables with the audit block | — | INT | Optimistic-locking counter. On the 16 tables with a `tr_touch_<table>` trigger it is incremented on every `UPDATE` (on `booking.booking` only when the `UPDATE` did not change it, 045); in payment-service `EfUnitOfWork` increments it and EF Core uses it as concurrency token, and `booking.booking` is the `@Version` of `BookingJpaEntity` (BIZ-09): a stale value answers 409 in both. On the other tables (lookup tables, `booking_service`, the `notification` tables) it stays at 1, and the other Java tables do not check it. | Starts at 1 |
